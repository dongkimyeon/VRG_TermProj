# W3.5 계산 비용 (2026-11-06, 창 없는 측정, FPS 미검증)

사용자 요청: 화면 없이 계산 쪽만. 창 없는 L_Test(`-game -NullRHI`, 32랙·33210셀·dt 0.02 s, 600스텝, 내부 3 mm 누수는 0.2 s에 시작)로 스텝 비용을 구간별로 재고 큰 것부터 줄였다. 물리·격자·dt·허용치·정밀도는 바꾸지 않았다.

## 바꾼 것

1. **물 노출 관측(W4-1 이후 매 스텝, W4 끔에서도):** `FWaterExposureSnapshot::IsValid`의 중복 대상 검사가 대상 1227개를 문자열로 쌍마다 비교(O(N²))해 23.6 ms/스텝이었다. 해시 집합으로 바꿨다(같은 판정). 관측마다 상태 모델 전체(1227개 스냅샷 2개)를 복사하던 것도 없앴다(`Step`은 실패 시 상태를 바꾸지 않는 원자적 함수라 결과 같음).
2. **랙 내부 수송 계수 재사용:** `InRackTransport::Build`가 읽는 모든 값(배관 유량·양 끝 노드·누수 유량·노드 불균형·밀도·비열)이 비트 단위로(memcmp) 같으면 이전 출력을 복사한다. 수력이 다시 풀리지 않는 정상 운전에서 1.9 → 0.4 ms. 누수 중에는 망 전체를 매 스텝 다시 풀어 다른 줄 유량 끝자리도 바뀌므로 거의 재사용되지 않는다. `vrg.Perf.TrayTransportReuse 0|1`(기본 1).
3. **랙 병렬:** 수송 계수 만들기, 트레이 스텝 한계, 랙 열모델 스텝을 랙마다 `ParallelFor`로. 각 랙은 자기 모델·입력·랙별 칸만 쓰고, 합계(IT, 손실, 누수 열, 장부)는 원래와 같은 랙 순서로 더한다. `vrg.Perf.RackParallel 0|1`(기본 1).
   - 규약 5 해석: 병렬 작업은 UObject 함수를 부르지 않지만 랙 액터 안의 일반 C++ 모델 메모리를 랙별로 나눠 읽고 쓴다(게임 스레드는 기다림). 사용자 확인 전이다. 아니라고 하면 `vrg.Perf.RackParallel 0` 기본으로 되돌린다.
   - 차이: 한 랙의 스텝이 실패하면(ensure 경로) 예전엔 뒤쪽 랙을 돌리지 않았고, 지금은 모두 돈 뒤 같은 스텝을 거절한다.
4. **계측:** `vrg.Air.RunSteps` 끝에 `[VrgCost]` 표(구간: EvalBefore, WaterPower, Inventory, PlantBefore, Bridge, PlantAfter, Water, AirFlowView, EvalAfter, 안쪽 세부, 수송 재사용 수). `EvalAfterStep`(센서·장애·W5)은 기존 `CouplingMs`에서 빠져 있어 따로 잰다(0.5~0.7 ms).

## FPS (미검증, 추정만)

프레임 = 스텝 n개 × 스텝 비용 s + 렌더 r, 실시간이면 n = 프레임/20 ms라 프레임 ≈ r / (1 − s/20). 2026-11-01 측정(정상 19.8 ms·s 14.2)에서 r ≈ 5.7 ms로 보면, 누수 s 16.0 → 약 28 ms(약 35 FPS), 누수 + W4 s 17.2 → 약 40 ms(약 25 FPS), 정상 s 12.3 → 약 15 ms. **이 수식과 r은 추정이다.** 2026-11-01 누수 78.6 ms는 s 17.7에서 한 프레임 최대 4스텝 상한에 걸린 값과 맞는다. 화면 측정 전에는 30 FPS 달성으로 쓰지 않는다. 절차는 `docs/기록/확인절차/W35_계산비용_FPS확인_2026-11-06.md`.

## 실행 중 실수 (기록)

- 측정 스크립트가 게임 프로세스를 못 끝내 6개가 동시에 돌았고(종료 명령 실패), 그동안의 측정과 빌드(DLL 잠김)가 오염됐다. 로그 이름으로 찾아 끝내고 남았는지 확인하게 바꿨다.
