## S5-A 구현·실행·검증 (2026-09-22)

`FFixedOctreeGrid`는 기존 균일 셀 각각을 루트로 하는 옥트리 묶음이다.
직육면체 도메인을 그대로 덮고, 랙 영역과 양의 체적으로 겹치는 셀만 8분할한다.
노드·부모·자식·리프는 선형 인덱스, 리프 순서는 Morton 코드로 구성한다.
온도 K와 고체 마스크는 SoA이며 균일 격자에서 읽기 전용으로 복사한다.
되돌릴 때는 체적 가중 평균을 쓴다. 열량은 고체를 제외한 ρ·cp·V·(T−기준온도)다.

**이번 완료 범위는 고정 격자 구성과 보존 전송이다.** 복사는 세부 온도 정보를
새로 만들지 않고, 고체 판정도 원래 균일 셀을 상속한다. 압력·속도·이류의 옥트리
시간 적분은 없다. 2:1 밸런스, 이웃·면 인덱스와 비균일 압력 연산자는 S5-B,
실행 중 분할·병합과 재투영은 S5-C에서 구현한다. 기존 균일 솔버와 통합 시계는 유지한다.

깊이는 0~6, 기본 리프 예산은 60,000개(상한 1,000,000개)다.
예산 초과 시 부분 트리를 내보내지 않고 실패를 표시한다.
국소 정밀화 테스트는 루트 6개에서 리프 20개, 최소 셀 폭 0.075 m다
(같은 최소 폭으로 전역 정밀화하면 384개). 이 수치는 성능 보장값이 아니다.

디버그 사용법:

1. 레벨에 `FixedOctreeDebugActor`를 추가하고 `AirField`에 기존 공기 액터를 지정한다.
   공기 액터가 정확히 하나면 자동 선택한다. 편집 뷰포트는 실시간 갱신을 켠다.
2. `RefinementDepth`와 `RackPaddingM`으로 랙 주변 범위를 정한다. 랙의 회전·스케일을
   포함한 월드 AABB를 공기 도메인 상대 m 좌표로 변환한다.
3. 깊이별 색상의 와이어프레임을 확인한다. `bDrawCoarseCells`는 기본 꺼짐,
   `MaxDrawnLeaves`는 기본 3,000개이며 표시만 제한한다.
4. 랙 이동·공기 격자 변경 뒤 `RebuildOctree`를 누르면 다음 틱에 재구축한다.
   `ActiveLeafCount`와 `BuildStatus`에서 전체 리프 수·오류를 확인한다.
   PIE에서는 재구축 시점의 균일 온도 스냅샷과 열량 차이(J)를 표시한다.

자동화 8건 (`VRG.Air.Octree.Fixed`): 도메인 빈틈·중복/부모자식/Morton,
국소 정밀화, 깊이 0 동일성, 열량·체적 가중 복원, 정지 열원 해석해,
잘못된 설정·예산 거부, 호환되지 않는 전송 거부, 실제 액터 재구축.
정지 열원은 균일 솔버의 열원 주입 결과를 전송하여 138.38 J 해석해와 비교한다.
**독립적인 옥트리 CFD 해와의 비교는 아니다.** 액터 테스트는 이동·90도 회전된 랙,
표시 상한과 토폴로지 예산 분리, 원본 필드·외부 시계 설정 보존을 확인한다.


빌드 성공, 전체 **63건 성공 / 실패 0 / 미실행 0**, 종료 코드 0.
리포트는 성공 61건 + 경고 동반 성공 2건이다. 기존 `Air.Energy.ClosedBoxConservation`과
`Air.Solid.EnergyConservation` 실행 중 엔진의 외부 HTTP 연결 확인이 시간 초과했다.
신규 8건은 경고 없이 성공했다. 결과는 `Saved/Automation/S5A-Full/index.json`과
`Saved/Logs/VRG_TermProj.log`에 있으며 생성물은 커밋하지 않는다.
NullRHI로 액터 표시 코드 경로까지 실행했지만 화면 품질·실제 렌더 성능은 미검증이다.

## S5-B 구현·실행·검증 (2026-09-22)

고정 옥트리에 **2:1 밸런스**, **면·이웃 인덱스 배열**, **비균일 압력 연산자**를 얹었다.
S5-A의 토폴로지와 보존 전송은 그대로 두고 그 위에 쌓았다.

**2:1 밸런스.** 면을 맞댄 두 리프의 깊이 차를 1 이하로 만든다. 박스 세분이 끝난 뒤
위반 리프를 모아 쪼개고, 그 때문에 새로 생긴 위반을 다시 훑는 식으로 변화가 없을 때까지
돈다. 깊이 상한이 있어 반복은 반드시 끝난다. 밸런스 분할도 리프 예산에 포함되며,
예산을 넘기면 S5-A와 똑같이 **부분 트리를 내보내지 않고** 실패를 표시한다.
없으면 굵은 셀 하나가 4개·16개·64개짜리 면과 맞닿아 연산자가 깊이 차마다 경우를 나눠야 한다.

**면·이웃 인덱스 (D7).** 면은 `FFixedOctreeFace`(LeafLow/LeafHigh/Axis/Area/Distance)로
한 번만 만들고, 리프별 참조는 CSR(`LeafFaceStart` + `LeafFaceIndices`)로 둔다.
중복을 피하는 규칙은 둘이다 — 깊이가 같으면 축의 + 쪽 리프가 만들고, 깊이가 다르면
**잘은 쪽**이 만든다 (굵은 쪽은 같은 깊이 이웃을 못 찾고 지나간다).
구축용 (깊이, Morton) 조회표는 `Build` 끝에서 버린다. 남겨 두면 솔버가 그걸로
이웃을 찾게 되고 그건 D7 위반이다. 솔버는 위 두 배열만 읽는다.

**비균일 압력 연산자.** 유한체적 두점 플럭스(TPFA)다.

    (L X)_i = (1/V_i) * sum_f T_f * (X_other - X_i),   T_f = Area_f / Distance_f

`T_f`는 면이 들고 있고 양쪽 리프가 **같은 값을 읽는다** (규약 6). 그래서 안쪽 플럭스가
쌍으로 상쇄되어 `sum_i V_i (L X)_i`가 항등적으로 0이다. 보존 잔차가 반올림인 것은
물리가 맞다는 뜻이 아니라 장부가 어긋나지 않는다는 뜻이다.
깊이 0에서는 `T_f = h^2/h = h`, `V = h^3`이라 기존 균일 연산자와 **같은 식**이 되고,
실제로 고체를 섞어도 차이가 **정확히 0**으로 측정된다.

**정확도는 비정합 면에서 1차다.** 두점 플럭스는 두 셀 중심을 잇는 선분이 면 중심을
지날 때만 2차인데, 깊이가 다른 면에서는 굵은 셀 중심이 면 중심에서 옆으로 벗어난다.
그래서 "선형장은 정확히 조화롭다" 같은 패치 테스트를 걸지 않았다 — 면에 평행한
방향으로 기울기가 있으면 실제로 성립하지 않는다. 손으로 확인하면 2:1 비정합 면에서
잘은 셀 하나에 `h^2/3`만큼 남는다. 개선하려면 다점 플럭스나 보간 스텐실이 필요하고
그건 별도 작업이다. **여기서 "비균일 격자로 계산한다"는 것은 이 1차 근사를 뜻한다.**

**솔버는 완화 Jacobi 그대로다 (D6).** 읽기/쓰기 버퍼가 분리돼 있어 균일 코드와 같은
구조로 돈다. 다만 셀 크기가 섞여 있어 두 가지가 바뀐다 — 해의 상수 자유도를 없앨 때
**체적 가중 평균**을 빼고, 해가 존재할 조건도 `sum(B)=0`이 아니라 `sum(V_i B_i)=0`이다.
단순 평균을 쓰면 잘은 영역에 가중치가 쏠린다. 종료 조건은 D5대로
정규화 잔차 목표 + 반복 상한이고 수렴 실패를 결과에 표시한다.

**이번 완료 범위는 연산자까지다.** 옥트리 위의 면 속도·이류·투영 한 스텝 전체는 없다.
실행 중 분할·병합과 재투영은 S5-C다. 기존 균일 솔버와 통합 시계는 그대로 돈다.

디버그 사용법 (S5-A에 이어서):

5. 상태 줄에 `면 N개 (비정합 M, 2:1 분할 K)`가 함께 나온다. 비정합이 0이면
   사실상 균일 격자라서 S5-B가 하는 일이 없다는 뜻이다.
6. `bDrawHangingFaces`를 켜면 비정합 면 중심에 분홍 점이 찍힌다. 잘은 쪽 면적이라
   굵은 면 하나에 점이 네 개 찍힌다. `MaxDrawnLeaves`가 이 점 수도 함께 제한한다.
7. `CheckPoissonOperator` 버튼은 **물리를 푸는 것이 아니라** 연산자 점검이다.
   리프 좌표에서 만든 합성장 X로 `B = L(X)`를 만들어 다시 풀고, 보존 잔차와
   되돌린 오차를 `OperatorStatus`에 적는다. PIE가 아니어도 돈다.
   `PreviewResidualTarget`(기본 1e-5)과 `PreviewMaxIterations`(기본 2000)로 종료를 정하며,
   못 미치면 "수렴 실패"라고 적는다 (D5). 여기 반복 수는 성능 보장값이 아니다.

자동화 7건 추가 (`VRG.Air.Octree.Fixed` 2건 + `VRG.Air.Octree.Poisson` 5건):
2:1 밸런스, 리프별 면적 폐합, 깊이 0 연산자 동일성, 보존·대칭·상수장,
깊이 0 코사인 해석해, 정제 격자 제조해 일관성, 수렴 실패·부적합 우변 표시.

**제조해 테스트는 이산화 정확도가 아니라 솔버 일관성을 잰다.** `B = L(X)`로 만든
우변이라 반드시 적합하고, 풀면 X가 되돌아오는 게 당연하다. 이게 재는 것은
연산자와 솔버가 같은 방정식을 보고 있는지다. **독립적인 옥트리 CFD 해와의 비교는 아니다.**
물리 정확도를 담당하는 것은 깊이 0 코사인 해석해 한 건뿐이고, 그건 정제 격자를 안 쓴다.



빌드 성공, 전체 **70건 성공 / 실패 0 / 미실행 0 / 경고 0**, 종료 코드 0.
S5-A 때 있던 외부 HTTP 시간 초과 경고 2건은 이번 실행에서는 나오지 않았다
(엔진의 네트워크 확인이라 코드와 무관하며, 다시 날 수 있다).
결과는 `Saved/Automation/S5B-Full/index.json`에 있으며 생성물은 커밋하지 않는다.
NullRHI라 화면 품질과 실제 렌더 성능은 여전히 미검증이다.

## 2-1 압력 멀티그리드 (2026-09-23)

**증상.** L_Test에서 압력이 매 스텝 반복 상한(400회)에 걸리고 정규화 잔차가 약 1e-4에서 멈췄다.
화면에 "압력 수렴 실패 - 속도장 믿지 말 것"이 떴다 (D5). 랙을 고체로 막아 영역이 불규칙해지면
완화 Jacobi가 매끄러운 오차를 O(N^(2/3)) 스윕에 걸쳐서야 줄이기 때문이다. 상한을 올리는 것은 해결이 아니다.

**해법.** `Simulation/Air/MultigridPoissonSolver.*` — 기하(집적) 멀티그리드를 전처리로 쓰는 공액기울기법(MG-PCG).
- 연산자를 `(1/V_i) Σ T_ij (X_j − X_i) = B_i` 일반형(CSR, 유체 셀만 압축 인덱스)으로 둔다. 균일 MAC(T=h, V=h³)과
  S5-B 옥트리 TPFA가 같은 형태라 S5-C에서도 같은 코드를 쓴다.
- 굵은 층은 2x2x2 집적. **블록 안에서 열린 면으로 이어진 셀끼리만** 합친다. 얇은 벽 양쪽을 한 셀로 합치면
  보정이 벽을 넘어 새어 `Air.Solid.BlocksFlow`(벽 너머 온도 불변, 1e-9 K)가 깨졌다 — 실제로 겪었다.
- 굵은 면 투과율은 덮인 열린 가는 면의 Σ(T_f·d_f)/D_IJ (재이산화). 상수 보간의 Galerkin 곱은 두 배 뻣뻣하다.
- 매끄럽히기는 모든 층에서 **완화 Jacobi**(ω=2/3, 앞뒤 2회, 읽기/쓰기 버퍼 분리). 굵은 층 끝은 60회.
- **D6 해석:** D6의 요지는 "Red-Black 같은 순서 의존 반복을 쓰지 않는다(옥트리에서 2색 분할 불가)"이다.
  멀티그리드의 스무더가 Jacobi이므로 D6을 지킨다. CG 외곽 반복은 내적 리덕션을 더할 뿐 순서 의존이 없다.
- D5: 종료는 기존과 같은 정규화 잔차(max|LX−B|/max|B|, 유체 셀) + 반복 상한(MG-PCG 반복 수). 실패는 결과와
  **로그**(첫 실패와 100회마다)에 남긴다. 무인 실행에서 HUD만으로는 실패를 볼 수 없었다.
- 기본값: `FAirSolver`와 액터 모두 MG-PCG (`vrg.Pressure.Multigrid 1`). 0이면 S3 Jacobi(CPU/GPU) 기준 경로.
  실시간 목표는 2e-5/400회 -> **1e-6/100회**로 조였다.

**검증** (`VRG.Air.Poisson.MultigridSolidsAndScaling`):

| 경우 | 결과 |
|---|---|
| 16³ 코사인 해석해 | V-cycle 25회 / MG-PCG 14회, 정규화 오차 3.70e-12 / 5.04e-13 (해 최대 0.9856 기준) |
| 랙 줄 고체 20x30x10 (유체 5460셀, 4층) | MG-PCG 20회, **S3 연산자로 잰** 잔차 7.97e-11, 제조해 오차 3.28e-11 |
| 같은 모양 40x60x20 (셀 8배, 45840셀, 5층) | MG-PCG 22회 — 반복 수가 격자와 거의 무관 |
| 같은 문제 완화 Jacobi | 4000회에 목표 1e-6 미달 (1.89e-6) |
| 상한 2회 | 수렴 실패로 표시 (D5) |

기존 공기 테스트는 전부 MG-PCG 경로로 다시 통과했다.

- 1e-6에서 예열 1500스텝 + 측정 8초 동안 **수렴 실패 0회**(로그 기준). 스텝이 도는 프레임의 95%는 14.2 ms다.
- **2-3 해결 (Draw 68 ms):** 원인은 GPU 압력 경로가 덩어리마다 `BlockUntilGPUIdle`로 렌더 스레드를 붙잡은 것이다.
  GJ 메시가 아니다. MG-PCG는 CPU라 Draw가 3.8~4.6 ms로 돌아왔다.
- 압력 외 나머지(이류·부력·투영)는 여전히 CPU FP64다. GPU Jacobi 경로는 비교 기준으로 남긴다(`vrg.Pressure.Validate`).

## S5-C 옥트리 전체 적분 (2026-09-23)

`FOctreeAirSolver`는 면 법선 속도·리프 온도 SoA를 적분한다. 운동량 풍상 플럭스 증분 →
Boussinesq 부력 → MG-PCG 압력 투영 → 보존형 온도 플럭스 → 체적 열원 → CRAH 순서다.
압력 CSR은 TPFA 면의 면적/중심거리로 만들고 BoxMin/BoxSize로 집적한다.
MG의 Neumann 호환성 검사는 비균일 체적 가중 합으로 교정했다. 비호환 우변을 임의로 투영하고
성공했다고 보고하지 않는다. Jacobi 스무더, 단일 외부 시계, SI/K, D1~D10을 유지한다.

런타임 `FAirSolver::AdaptOctree` / `AAirFieldDebugActor::ApplyOctreeRefinement`는 새 2:1 토폴로지를
별도로 만들고 동일 루트 안 리프의 겹친 체적을 사용해 온도·셀 속도를 전송한다.
온도는 체적 보존, 속도는 새 면으로 보간 후 재투영한다. 시계와 누적 열장부를 초기화하지 않는다.
예산 초과/재투영 실패는 기존 상태를 유지한다. 고체/유체가 섞인 리프의 병합은 거부한다.

사용: AirFieldDebugActor의 `Use Octree Solver`를 켜고 ResetSim, Octree Depth/Max Leaves를 정한다.
`Octree Refinement Boxes M`은 공기 액터 원점 기준 **미터** AABB다. 실행 중 상자를 추가/제거한 뒤
ApplyOctreeRefinement로 분할/병합한다. 이 배열 편집만으로는 상태를 리셋하지 않는다.
균일 경로는 기본값/비교 기준으로 남는다. 기존 CouplingBridge는 루트 셀의 W/UA를 넘기고
옥트리는 자식 체적 비율로 분배한다. 렌더·흡기 샘플은 리프를 루트에 체적 평균한 사본을 쓴다.
따라서 슬롯/고체 경계는 아직 루트 격자 해상도다. 상세 리프 흡기 계측을 구현했다고 주장하지 않는다.
기존 FixedOctreeDebugActor는 S5-A 미리보기이며 S5-C 토폴로지와 별개다. 실제 해석 상태는 AirField HUD에 나온다.

수치 한계: TPFA 비정합 면 1차, 온도·운동량 이류 1차. 속도 전송 후 운동에너지까지 보존하지는 않는다.
수치 안정성은 `dt*sum(outgoing u*A)/V <= 0.5`로 내부 서브스텝을 사용하며 전체 외부 dt를 소비한다.
이는 장비 측정치가 아닌 명시적 풍상차분의 CFL 조건에 여유를 둔 수치 설정이다.
균일 속도 이류는 기존 반라그랑주, 옥트리는 풍상 증분이므로 유동 결과가 비트 동일하다고 주장하지 않는다.
장비 물성·실험으로 보정되지 않은 모델인 만큼 보존 잔차만으로 실제 데이터센터 정확도를 보장하지 않는다.

## S5-D 온도·속도 기반 자동 적응 (2026-09-27)

`FOctreeAdaptController`(`Simulation/Air/OctreeAdaptController.*`)가 균일 루트 내보내기에서 루트 셀마다 지표를 재고
어느 루트를 정밀화할지 고른다. 실제 분할·병합은 S5-C의 보존 전송·재투영이 한다. `FAirSolver`의 옥트리 경로가 스텝 뒤에
같은 dt로 호출하므로 통합 액터 아래에서도 돌고 시계는 건드리지 않는다(규약 4).

- 지표(SI): |∇T| [K/m] (공기 이웃 중심 차분, 벽·고체 옆은 한쪽 차분), |u| [m/s] (면 속도의 셀 중심 평균).
- **채터링 방지 세 겹.** (1) 히스테리시스: 지표가 Refine 문턱을 넘으면 정밀화, 둘 다 Coarsen 문턱 아래일 때만 병합
  (Coarsen < Refine가 아니면 설정을 거부). (2) 보류 시간 `MinHoldS`: 바뀐 상태를 그만큼은 유지. (3) 평가 간격 `IntervalS`:
  격자 변경은 간격마다 최대 한 번.
- 예산 `MaxRefinedRoots`(0 = 없음): 넘으면 정규화 지표가 큰 순서로 남긴다. 보류 시간보다 우선한다(하드 한계).
- 제안 → 확정: 옥트리가 실제로 적응했을 때만 확정한다. 리프 예산 등으로 실패하면 제안을 버리고 기존 격자를 유지하며
  로그(첫 회와 100회마다)와 HUD에 남긴다(D5 정신).
- 사용: `AirFieldDebugActor`의 `bUseOctreeSolver` + `bAutoAdaptOctree`, `OctreeAdaptSettings`, ResetSim. 수동 상자
  (`OctreeRefinementBoxesM`)는 그대로 더해진다. 기본 문턱 8/4 K/m, 1/0.5 m/s, 보류 2 s, 간격 0.5 s는 **출발값**이며 보정한 값이 아니다.

**완료 조건 점검 (S5 전체 조건의 D 몫).** 격자를 바꿔도 열량이 사라지지 않는다(24번 재격자 뒤 잔차 -2.8e-14).
핫스팟 판정: 같은 입력·같은 스텝의 균일 기준과 최고 온도 셀이 같고, 값은 +0.34 K(상승분 6.33 K의 5.4%) 차이다.
이 차이는 옥트리 운동량 이류가 균일 경로(반라그랑주)와 다르고 비정합 면이 1차이기 때문이며(S5-B/C 절), **같은 정확도
조건의 비교가 아니다** — 정밀화한 쪽이 더 정확하다고 주장하지 않는다. 독립적인 기준 해(더 촘촘한 균일 격자 등)와의
비교는 아직 없다.

**한계.** 지표는 루트 해상도(0.25 m)에서만 잰다 — 이미 정밀화한 리프 안의 구조는 보지 않는다. 깊이는 설정한 MaxDepth
하나로 고정이다(루트마다 다른 깊이를 고르지 않는다). 옥트리 경로는 여전히 덕트(랙 팬 관통 기류·CRAH 유닛)를 지원하지 않아
L_Test 통합 구성에는 쓸 수 없다. S5-E(성능 기반 LOD)는 남았다.

검증: `VRG.Air.Octree.AutoAdapt` 2건(수치는 오차 기준표). 전체 `VRG` Automation **98 성공 / 실패 0**
(2건은 엔진 외부 HTTP 확인 시간 초과 경고 동반, 코드와 무관). `Saved/Automation/S5D_All`.


## S5-E 성능 기반 LOD (2026-09-27)

`FOctreeAdaptSettings::TargetStepMs`(0 = 끔, 기본 끔)를 주면 평가마다 직전 구간의 옥트리 스텝 평균 비용 [ms]으로 루트 예산을
조절한다. 목표 × (1 + `LodBand`, 기본 0.2)를 넘으면 예산 = 현재 정밀 루트의 80%, 목표 × (1 − LodBand) 아래면 예산 × 1.25 + 1
(`MaxRefinedRoots`까지). 대역 안에서는 그대로다(히스테리시스). 예산은 S5-D의 예산 규칙대로 지표가 큰 루트부터 남긴다.
**셀 수·계산 시간 기록**: 평가마다 (시각, 리프 수, 평균 스텝 ms, 예산)을 `GetLodHistory()`에 쌓고 HUD `[S5-E]`에 최근 값을 띄운다.
비용은 솔버 안에서 잰 벽시계 시간이며 전역을 쓰지 않는다(규약 5).

- **켜면 재현성이 깨진다.** 벽시계 시간이 기계·실행마다 달라 격자가 달라진다. 반복 비교(S6 재실행)에서는 끈다. 그래서 기본 끔이다.
- 제어 법칙은 비용을 입력으로 받게 해 합성 비용으로 결정적으로 검증했다(40루트에서 정착, 뒤 절반 변경 0).
  실제 솔버 기록(12x6x8, 목표 1.0 ms): 리프 576 → 1143, 스텝 0.17 ~ 0.89 ms, 열수지 2.2e-14.
  **측정값이며 보장값이 아니다** (D10). 목표가 정밀화 없는 기본 비용보다 낮으면 예산이 0으로 가서 정밀화하지 않는다(실제로 확인).
- 한계: 비용 모델이 없다(측정만 쓴다). 깊이는 고정이고 예산만 바꾼다. 옥트리 경로는 여전히 덕트 미지원이라 L_Test 통합 구성의
  실제 프레임 예산에는 아직 연결할 수 없다.

**S5 전체.** A~E 구현·테스트 완료. 남은 조건: "A/B 비교는 같은 정확도 조건에서" — 옥트리 경로와 균일 경로는 이류 방식이 달라
같은 정확도 조건이 아니고(S5-C 절), 독립 기준 해와의 비교가 없다. 옥트리 덕트 지원 뒤 L_Test에서 비교할 수 있다.
전체 `VRG` Automation **99 성공 / 실패 0** (1건 엔진 HTTP 경고 동반). `Saved/Automation/S5E_All`.

## 공기 솔버 멀티코어 (2026-09-27)

**측정 먼저.** 32랙 L_Test(격자 54x41x15 = 33210셀) 한 스텝 24.1 ms 중 속도 이류 10.2, 투영(압력 포함) 10.3, 온도 수송 1.6,

## 난류 모델: Chen-Xu 0-방정식 (2026-09-27)

계획은 `docs/기록/확인절차/인계_2026-09-27.md` 2단계. 공기 솔버가 비점성(수치 확산만)이던 것을 실내 기류용 0-방정식 모델로 바꿨다.
- 모델: **nu_t = 0.03874 · |V| · l** (Q. Chen, W. Xu, Energy and Buildings 28 (1998) 137-144). |V|는 셀 중심 속도 크기,
  l은 가장 가까운 벽(도메인 경계·고체 셀)까지의 거리다(`Simulation/Air/WallDistance.*`, 격자에 벽 한 겹을 두른 정확한
  유클리드 거리 변환 − h/2. 축 방향 벽은 정확, 모서리·대각은 h/2 안). 거리장은 고체가 바뀔 때만 다시 계산한다.
- 분자 물성은 300 K 공기(Incropera & DeWitt 표 A.4): nu 15.89e-6, alpha 22.5e-6 m2/s. **Pr_t 0.9는 일반적 가정값**이다(논문 값이 아니다).
- 운동량: 면 속도에 nu_mol + nu_t 확산(라플라시안 형태). **응력 텐서의 전치항은 뺐다**(가변 점성에서 엄밀하지 않다).
  벽·고체의 접선 방향은 no-slip(반 칸 밖 유령값 −u), 벽·덕트 면은 경계값 그대로(Dirichlet). 위치: 부력 뒤, 투영 앞.
- 온도: alpha_mol + nu_t/Pr_t 확산을 **같은 면 플럭스**에 더한다(규약 6). 벽·고체·덕트 면에는 확산 플럭스가 없다(단열). 열수지 장부 불변.
- 명시적이라 부분 스텝: 운동량은 10·nu_max·dt/h² ≤ 0.9, 온도는 기존 CFL 조건에 6·alpha_max·dt/h²를 더한다.
- 스위치: 솔버 기본은 **꺼짐**(`FAirTurbulenceSettings::bEnabled`) — 솔버를 직접 부르는 기존 자동화 테스트는 비점성 기준 그대로다
  (끄면 새 코드가 돌지 않는다). 액터는 `vrg.Air.Turbulence`(기본 **1**)로 켠다. 옥트리 경로는 난류를 무시한다.

검증 (`VRG.Air.Turbulence.*` 4건, 오차 기준표):
- 벽 거리 해석값(빈 상자, 고체 한 칸의 면/모서리/꼭짓점 이웃) 오차 0.
- 운동량·온도 확산 연산자가 이산 고유모드(no-slip 사인 / 단열 코사인)를 **정확한 이산 감쇠율**로 줄인다(2.3e-15, 2.7e-14).
  이것은 이산화가 설계대로 됐다는 뜻이지 난류 모델이 실제 기류를 맞힌다는 뜻이 아니다.
- 닫힌 상자(고체·부력·열원 2 kW, 10 s): 열수지 2.40e-14, 발산 2.72e-11, nu_t 최대 0.0214 m2/s. 최고 온도 47.006 C (비점성 47.133 C).
- **"UE 값 = 실제"를 보장하지 않는다.** Chen-Xu 계수는 실내 기류 실험에 맞춘 경험식이며 이 방에 대해 보정·검증한 적이 없다.

L_Test(32랙, 33210셀, `-game` 1280x720, 1500스텝 예열, 이 PC): nu_t **최대 0.137 / 평균 0.0159 m2/s**(계획 때 예상한 1e-3~1e-1 범위),
운동량 확산 부분 스텝 1, 온도 부분 스텝 2. 스텝 평균 **8.73 ms**(끄고 9.50 ms): 난류 단계 1.01 ms가 늘었지만 투영이 5.69 -> 4.02 ms로 줄었다
(속도장이 매끄러워져 압력 MG가 일찍 수렴한 것으로 보이며, 원인을 따로 검증하지는 않았다). 프레임 중앙값 6.16 ms / 95% 13.23 ms.
t=30 s 랙 흡기 20.28~22.68 C(끄고 20.14~22.73 C), 열수지 잔차 -1.31e-14. 전체 `VRG` Automation **106 성공 / 실패 0 / 경고 0**.
측정값이며 보장값이 아니다(D10). 격자 해상도에 따른 차이는 3단계(격자 수렴 검사)에서 본다.


## 격자 수렴 검사 (2026-09-27)

계획은 `docs/기록/확인절차/인계_2026-09-27.md` 3단계. 32랙 L_Test를 같은 방(13.5 x 10.25 x 3.75 m)에서 h 0.25 m(54x41x15 = 33210셀)와
0.125 m(108x82x30 = 265680셀)로, 난류 켬/끔 각각 300 s(15000스텝) 돌렸다. 인로우 CRAH 8대, 랙별 라디에이터가 아닌 기본 구성 그대로.
- 재현: `vrg.Air.Turbulence 0|1, vrg.Air.CellSize <h> 0.25, vrg.Air.RunSteps 15000`. 두 번째 인자는 도메인 올림 단위다 —
  그냥 ceil(span/h)로 맞추면 h마다 천장 높이가 달라져(3.75 대 3.625 m) 해상도만 바꾼 비교가 아니게 된다(실제로 겪었다).
- 지표: 랙 32대 + 스파인 2대 흡기의 **마지막 100 s 시간 평균**(실행 간 흔들림 때문에 순간값은 쓰지 않는다, 앞 절).

| 구성 | 흡기 평균 / 최저 / 최고 °C | CRAH 제거 | 전역 잔차 |
|---|---|---|---|
| 0.25 m 난류 | 26.54 / 24.39 / 31.17 | 499.9 kW | 3.93e-14 |
| 0.125 m 난류 | 26.41 / 24.00 / 28.70 | 506.1 kW | 4.14e-14 |
| 0.25 m 비점성 | 26.74 / 23.31 / 33.53 | 497.9 kW | 4.21e-14 |
| 0.125 m 비점성 | 27.51 / 24.65 / 31.74 | 512.2 kW | 4.82e-14 |

같은 랙끼리 0.25 → 0.125 m 차이: **난류 켬 평균 −0.13 K, RMS 1.51 K, 최대 3.58 K** / 비점성 평균 +0.77 K, RMS 2.52 K, 최대 3.92 K.

**결론.**
- 방 단위 값(흡기 평균, CRAH 제거열 1.2% 차)은 난류를 켜면 0.25 m에서 거의 격자에 무관하다. 비점성은 평균부터 0.8 K 움직인다.
  난류 모델이 격자 의존성을 줄인다는 것은 확인됐다.
- **랙 하나하나의 흡기는 0.25 m에서 수렴하지 않았다.** 난류를 켜도 랙별 RMS 1.5 K, 최대 3.6 K가 움직이고 가장 뜨거운 랙의 자리도 바뀐다
  (0.25 m: 줄 A 끝 y 4.62 m, 0.125 m: 줄 A 가운데 y 0.66 m). 흡기 상승분(공급 대비 2~9 K)에 비하면 큰 차이다. 핫스팟 판정에는 0.25 m가 부족하다.
- **0.125 m가 수렴했다는 뜻은 아니다.** 두 수준뿐이라 수렴 차수·외삽값을 낼 수 없다. 0.0833 m(약 90만 셀)는 격자 맞춤 상한(축당 128)을 넘고
  스텝 비용이 너무 커서 돌리지 않았다. 인로우 구성은 같은 설정도 실행마다 최고값이 약 0.5 K 흔들리므로 그 이하 차이는 구분하지 않는다.
- 계획의 판정대로 **4단계(GPU)로 촘촘한 격자를 실시간에 가깝게 만든다.** 0.125 m 스텝은 CPU 16코어에서 53 ms(단독 실행 측정)라
  20 ms 절벽(S7-5)의 2.7배다. (위 표의 실행은 네 개를 동시에 돌려 스텝 시간이 서로 방해받았으므로 시간 값은 쓰지 않는다.
  결과 수치는 병렬/직렬이 같은 값을 내므로 영향이 없다.)
- 측정값이며 보장값이 아니다. 보정되지 않은 모델의 격자 의존성 검사이지 실제 방 온도의 검증이 아니다.


## 4단계 진행: GPU FP64 압력 MG-PCG (2026-09-27)

계획은 `docs/기록/확인절차/인계_2026-09-27.md` "4단계 세부 계획". **필드도 FP64로 GPU에 둔다**(계획의 "필드 FP32"를 바꿈: FP32 온도는 300 K에서
분해능 약 3e-5 K라 보존 자체가 깨진다). 순서를 바꿔 압력(4d)을 먼저 했다 — 0.125 m 스텝 50 ms 중 32 ms라 가장 크고 가장 어렵다.

- **4a FP64 가능성**: UE 5.8 D3D12 SM6에서 `StructuredBuffer<double>` 셰이더가 컴파일·실행된다. FP64 덧셈·곱셈·나눗셈은 IEEE이고,
  셰이더 컴파일러가 `A*B+C`를 FMA 하나로 합친다(CPU를 `std::fma`로 계산하면 4096개 전부 비트 동일). 셰이더 매개변수 구조체는
  double 스칼라를 못 받으므로 스칼라도 버퍼로 넘긴다. HLSL은 double sqrt/exp/floor가 없다. 셰이더가 참조하는 매개변수는 분기에서
  안 읽어도 전부 바인딩해야 한다(안 하면 치명 오류) — 기본값으로 1원소 더미 버퍼를 묶는다.
- **4d 압력**: `VrgRender/VrgAirGpu.*` + `Shaders/Private/VrgAirMg.usf`. CPU `FMultigridPoisson`이 만든 계층(CSR)을 그대로 올리고
  (`ExportHierarchy`, 위상 변경 때만) CG·V-cycle을 같은 순서로 따라간다. 스무더는 완화 Jacobi(D6), 제한은 자식 목록 gather.
  수렴·파괴·부적합·영 우변 판정을 GPU 상태 스칼라가 하고, 그 뒤 커널은 조기 종료한다. 호스트는 덩어리(8회)마다 16개 스칼라만 읽는다(D5).
  리덕션은 그룹당 부분합 → 한 그룹이 고정 순서로 접는 두 단계(원자 연산 없음, 실행마다 같은 순서).
- 스위치: 액터 `vrg.Pressure.GpuMultigrid 0|1`(기본 **0**), 솔버 `SetUseGpuMultigrid`. GPU가 없거나 실패하면 CPU로 풀고 로그에 한 번 적는다.

**측정 (L_Test 32랙, 1500스텝, 이 PC, 측정값이며 보장값 아님 D10).** 결과(흡기 범위·전역 잔차·CRAH 제거)는 CPU/GPU 두 경로가 출력 자리수까지 같다.

| 격자 | 투영(압력 포함) CPU → GPU | 스텝 CPU → GPU | Draw (GPU 켬) |
|---|---|---|---|
| 0.25 m 33210셀 | 4.11 → **6.56 ms (느림)** | 8.81 → 11.34 ms | 5.8 → 10.6 ms |
| 0.125 m 265680셀 | 26.09 → 15.56 ms | 48.31 → 37.74 ms | 5.3 → **49.6 ms** |

단독 풀이(0에서 시작, 16회): CPU 50.0 ms / GPU 14.3 ms(`Gpu.Air.PressureTiming`). L_Test 0.125 m는 스텝당 7회.
**그래서 기본값을 켜지 않았다.** 0.25 m에서는 디스패치(반복당 약 53개)·동기화 비용이 계산보다 크고, 0.125 m에서도 스텝마다 격자 크기
배열을 올리고 내려받으며 렌더 스레드를 붙잡는다(Draw 49.6 ms). 20 ms 목표는 나머지 단계까지 GPU에 상주시키고(4b/4c/4e) 동기화를
스텝당 1~2번으로 줄여야 닿는다. 다음 할 일은 인계 문서에 있다.

GPU 테스트 실행(`-NullRHI` 없이, 창 없이):
일반 `VRG` 실행(-NullRHI)에서는 `VRG.Gpu.*` 3건이 "GPU 없음 - 건너뜀"을 남기고 성공한다. 전체 **110 성공 / 실패 0**, GPU 3건 성공.
`UnrealEditor.exe`를 `-log`와 함께 백그라운드로 띄우면 콘솔 제어 이벤트로 함께 죽는다(실제로 겪었다). 무인 측정은 `-log` 없이 `-abslog`만 쓴다.

### 4b/4c: 한 스텝 전체를 GPU에 상주 (2026-09-27)

`FVrgAirGpuSolver`(`VrgRender/VrgAirGpu.*`, 셰이더 `VrgAirStep.usf`)가 균일 격자 한 스텝을 FP64로 돈다: 난류 점성, 반라그랑주 속도 이류,
부력, 벽·덕트 경계, 운동량 확산, 발산·평균 빼기, 압력 MG-PCG(4d, 결과를 GPU 압력장에 바로 흩뿌림), 기울기 보정, 온도 풍상·확산 플럭스,
덕트 혼합·코일·팬, 보존형 갱신, 열원, 셀 코일. 커널마다 CPU `FAirSolver` 함수를 식과 연산 순서까지 따라간다(HLSL에 double sqrt가 없어
nu_t의 |V|는 float 초기값 + 뉴턴 두 번).
- `FAirSolver::StepOnGpu`가 CPU와 같은 규칙으로 부분 스텝 수·CFL·장부(열 유입·셀 코일·덕트 코일·팬)를 정한다. 덕트별 ε·팬 dT·열용량률은 CPU가 계산해 올린다.
- **CPU 격자는 거울이다.** 매 스텝 온도·면 속도를 내려받으므로 결합 다리·볼륨 렌더·스냅샷·장부 코드가 그대로다. `GetMutableGrid()`·초기화·고체 변경은
  다음 GPU 스텝 전에 전체를 다시 올리게 한다. 압력장은 GPU에만 있다(CPU 거울의 압력은 오래된 값, CPU 경로의 초기 추정값에만 쓰인다).
- 한 스텝에 동기화 3~4번: 시작 최대값(nu_t·|u|) → 속도·투영(+압력 덩어리마다) → 온도·열원·냉각 + 필드 내려받기.
  단계 중간에 실패하면 CPU 거울(스텝 전 상태)로 이번 스텝을 CPU가 돌고 다음 GPU 스텝 전에 다시 올린다.
- 스위치: 액터 `vrg.Air.Gpu 0|1`(기본 **0**), 솔버 `SetUseGpuStep`. 옥트리 경로는 대상이 아니다.

검증 `VRG.Gpu.Air.StepMatchesCpu`(고체·덕트 코일·팬 발열·열원·셀 코일·부력, 난류 끔/켬, 150스텝): 온도 차 2.8e-13 K, 속도 차 4.9e-15 m/s,
압력 반복 합이 CPU와 같고 GPU 쪽 장부도 반올림 수준으로 닫힌다(오차 기준표). 전체 `VRG`(NullRHI) **111 성공 / 실패 0**, GPU 4건 성공.

**L_Test 측정 (32랙, 1500스텝, 이 PC, 측정값이며 보장값 아님 D10).** 흡기 범위·CRAH 제거·전역 잔차가 CPU 경로와 같다(0.125 m 잔차 -6.25e-15 대 -6.19e-15).

| 격자 | 스텝 CPU → GPU | 프레임 중앙값 CPU → GPU | Draw (GPU) |
|---|---|---|---|
| 0.25 m 33210셀 | 8.81 → 9.28 ms | 5.52 → **19.07 ms (나빠짐)** | 17.2 ms |
| 0.125 m 265680셀 | 48.31 → **14.39 ms** | 208.0 → 58.8 ms | 35.2 ms |

- **0.125 m 스텝이 목표(20 ms) 안에 들어왔다.** 그러나 프레임은 58.8 ms(17 fps)다. 프레임 ≈ 프레임당 스텝 수 × 14.4 ms + 스텝 밖 약 15 ms이고,
  시계 되먹임(S7-5)으로 프레임당 약 3스텝에서 평형을 이룬다. 스텝 밖 비용의 대부분은 볼륨 렌더가 스텝마다 265680셀 텍스처를 CPU에서 만들어
  올리는 것으로 **추정**한다(따로 재지 않았다). 다음 할 일: 볼륨 렌더가 GPU 버퍼를 직접 읽기, 스텝 시작 동기화를 앞 스텝 내려받기에 합치기.
- 0.25 m에서는 GPU 스텝이 CPU보다 빠르지 않고 동기화가 렌더 스레드를 붙잡아 프레임이 나빠진다. 그래서 기본값은 CPU다.
  촘촘한 격자에서는 `vrg.Air.Gpu 1, vrg.Air.CellSize 0.125 0.25`로 켠다.

### 4f: 프레임 줄이기 (2026-09-27)

측정으로 원인을 먼저 가렸다. 0.125 m GPU에서 볼륨을 끄면 프레임이 58.8 → 35.7 ms라 볼륨 경로가 약 23 ms였고, 나머지는 셀 수에 비례하는
게임 스레드 작업(표시용 스냅샷을 프레임마다 여러 번 만들기)이었다.
- **표시용 스냅샷을 시뮬 시간당 한 번만 만든다.** 공기 HUD·볼륨 자동 색 범위(`GetDisplaySnapshot`), 통합 액터 HUD. 공개 `GetSnapshot()`은
  캐시하지 않는다(테스트가 격자를 직접 고친 뒤에도 정확해야 한다).
- **전체 격자 루프를 결정적 병렬로**: `MakeSnapshot`, `TotalThermalEnergyJ`(고정 블록 합 — 실행마다 같은 값, 직렬 합과는 반올림만 다름),
  `MaxAbsDivergencePerS`, `MaxAbsVelocityMs`, 볼륨 복셀·속도 텍스처 변환.
- **스텝 시작 동기화 제거**: 스텝 끝 그래프가 다음 스텝의 nu_t와 최대값을 계산해 필드와 함께 읽는다. 사이에 상태를 다시 올리거나 난류 설정이
  바뀌면 버리고 동기화한다. 같은 속도장에서 같은 커널이라 값이 같다. 난류 단계 1.67 → 0.28 ms.
- **고친 결함**: GPU 스텝과 CPU 스텝을 섞어 돌리면(`vrg.Air.Gpu` 1 → 0 → 1) GPU가 CPU가 바꾼 상태를 몰랐다. CPU 스텝이 돌 때 GPU 상태를
  더럽힘 표시한다. `StepMatchesCpu`에 10스텝마다 교대하는 경우를 넣었다(오차 기준표).
- **자동 선택** `vrg.Air.Gpu -1`(새 기본): 셀 수가 `vrg.Air.GpuAutoCells`(100000) 이상이면 GPU. 두 측정점(33210셀은 CPU, 265680셀은 GPU가 빠름)
  사이에서 고른 값이며 교차점을 잰 것은 아니다. 0/1로 강제할 수 있다.

| L_Test 32랙 (1500스텝 뒤 5 s, 1280x720, 이 PC) | 스텝 | 프레임 중앙값 / 95% |
|---|---|---|
| 0.25 m CPU (자동) | 8.97 ms | 5.87 / 12.94 ms |
| 0.125 m CPU | 48.31 ms | 208.0 ms |
| 0.125 m GPU, 4f 전 | 14.39 ms | 58.8 ms |
| **0.125 m GPU (자동), 4f 뒤** | 14.37 ms | **22.14 / 36.26 ms** |

결과(흡기 범위·CRAH 제거·전역 잔차 -6.19e-15)는 CPU 경로와 같다. 0.125 m는 중앙값 45 fps, 95%는 27.6 fps로 30 fps 최저선 근처다.
측정값이며 보장값이 아니다(D10). 전체 `VRG`(NullRHI) **111 성공 / 실패 0**, GPU 4건 성공.
남은 것(필요할 때): 볼륨 렌더가 GPU 버퍼를 직접 읽기(지금은 거울에서 텍스처를 다시 만들어 올린다), 압력 반복당 디스패치 줄이기.


## S5 마무리 5a: 옥트리 경로 덕트 (2026-09-27)

옥트리 공기 경로가 이제 팬 덕트(랙 관통 기류·CRAH 유닛)를 받는다. 전에는 거부하고 천장 코일로 대체했다.
- `FOctreeAirSolver::MapDucts`: 검증된 루트 덕트 면을 그 면 위에 놓인 옥트리 면(고체 리프 | 공기 리프)으로 옮긴다. 정밀화된 쪽은 루트 면 하나가
  잘은 면 4개가 된다. 위상이나 덕트 면 목록이 바뀔 때만 다시 짝짓는다. 공기 리프가 입력의 공기 셀과 다른 루트에 있거나 옮길 면이 없으면 거부하고
  로그에 남긴다(D5 정신, `WereDuctsRejected`).
- 속도: 덕트 면은 입력 속도로 고정되고 투영에서 0으로 지워지지 않는다. 투영 우변에는 공기 쪽 리프에만 플럭스가 들어간다.
- 운동량: 덕트 면으로도 풍상 운동량 플럭스를 넣는다(들어오는 공기는 덕트 속도, 나가는 공기는 셀 속도). 이게 없으면 배기 제트가 투영만으로 생긴다.
  **옥트리 운동량 이류는 1차 풍상이라 균일 경로(반라그랑주)보다 확산이 크다** — 배기 다음 면 속도가 덕트 속도의 47%(균일 경로 테스트는 50% 이상).
- 온도: 덕트마다 흡기 엔탈피를 한 번 합산 → 코일 ε → 팬 dT → 배기 면이 싣는다(규약 6, 균일 `AdvectTemperature`와 같은 식). 흡기 면은 CFL 계산에 들어간다.
  장부: 코일은 유출, 팬은 유입. `FAirSolver`가 코일·팬 값을 옥트리에서 받아 결합 다리의 전역 장부에 넘긴다.
- `FAirSolver`는 덕트를 옥트리 경로에서도 검증한다(검증이 옥트리 분기 앞으로 옮겨졌다). 통합 액터의 "옥트리면 CRAH 대신 천장 코일"은 없앴다.
- 곁가지로 고친 것: `FAirSolver::Step`이 일찍 끝나면 지난 스텝의 덕트 입력 포인터가 남을 수 있었다 — 스텝 시작에서 지운다.

같은 장면 A/B(오차 기준표 테스트, 500스텝): 덕트 코일 제거 균일 86.818 W / 옥트리 깊이 0 83.749 W / 깊이 1 82.572 W(-3.5% / -4.9%).
두 경로의 운동량 이류가 달라 같은 정확도 조건의 비교가 아니다. 난류는 옥트리 경로에서 여전히 무시된다.
L_Test 콘솔: `vrg.Air.Octree <깊이> [여유 m]`가 다음 시뮬레이션 진입 때 랙·스파인 상자(여유 포함) 주변을 정밀화한다(A/B용, 레벨은 그대로).
L_Test 깊이 1: 스텝 약 149 ms(옥트리 코드는 직렬 CPU) — 균일 0.125 m CPU 48 ms / GPU 14 ms보다 느리다.


## S5 마무리 5b: 옥트리 대 균일 A/B (2026-09-27)

같은 L_Test(32랙, 루트 54x41x15, 300 s, 비점성 — 옥트리 경로가 난류를 무시하므로 균일도 난류 끔 실행과 비교)를 균일 0.25 m / 옥트리(랙·스파인 주변
여유 0.5 m를 깊이 1 = 0.125 m로) / 균일 0.125 m로 돌렸다. 지표는 흡기 34곳의 마지막 100 s 시간 평균, 기준은 균일 0.125 m.

| 구성 | 방 평균 차 | 랙별 RMS | 최대 | 스텝 |
|---|---|---|---|---|
| 균일 0.25 m | -0.77 K | 2.52 K | 3.92 K | 9 ms (CPU) |
| 옥트리 (랙 주변 0.125 m) | -0.79 K | 2.30 K | 4.71 K | 139 ms (직렬 CPU) |
| 균일 0.125 m (기준) | — | — | — | 48 ms CPU / 14 ms GPU |

**결론: 랙 주변만 잘게 나눠서는 균일 0.125 m에 거의 가까워지지 않았다**(방 평균은 그대로, 랙별 RMS 0.2 K만 줄었다). 흡기를 정하는 재순환이
랙 주변만이 아니라 줄 위·통로 전체에서 일어나기 때문으로 **추정**한다. 비용은 균일 0.25 m의 15배, 균일 0.125 m GPU의 10배다.
그래서 촘촘한 격자가 필요하면 **GPU 균일 격자(4단계)를 쓴다.** 옥트리 경로는 검증 기준·실험용으로 남기고 더 키우지 않는다.
운동량 이류가 달라(1차 풍상 대 반라그랑주) 같은 정확도 조건의 비교가 아니다 — S5 완료 조건의 이 부분은 이 한계와 함께 닫는다.
