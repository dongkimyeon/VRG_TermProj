# 시각화·성능·외형 모델·패키징 기록

CLAUDE.md에서 2026-10-15에 옮겨 온 날짜별 작업 기록이다. 내용은 당시 기록이며, 지금 상태와 다를 수 있다
(최신 상태는 CLAUDE.md "현재 상태" 절). 정리 때 다른 PC 경로, 화면 도구 실패·재시도 문장, 로컬 로그 경로,
HMD 문구, 병합 전 원격 기록, 옛 성능 표는 지웠다. 전문은 git 기록(2026-10-15 이전 CLAUDE.md)에 있다.

## S7을 S5-C 앞으로 당긴 이유 (2026-09-22)

단계 순서를 벗어나 S7(시각화·성능)의 일부를 S5-C보다 먼저 한다. 이유는 둘이다.

첫째, **디버그 박스로는 옥트리 유동을 눈으로 검증할 수 없다.** S5-C는 옥트리 위에서
속도장을 풀고 재투영하는 단계인데, 지금 연속장 표시가 `DrawDebugSolidBox`라서
셀 하나가 드로우 호출 하나다. 옥트리로 셀을 잘게 쪼갤수록 그릴 수가 없어진다.
계산이 맞는지를 화면으로 볼 수 없으면 S5-C의 검증이 자동화 테스트 숫자에만 의존하게 된다.

둘째, **지금 격자를 키울 수 없다.** 아래 기준선대로 프레임이 이미 1.5 fps다.
옥트리의 목적이 "필요한 곳만 잘게 나눠 해상도를 올리는 것"인데, 해상도를 올릴
여유가 애초에 없으면 S5의 나머지가 의미를 잃는다.

순서를 바꿨을 뿐 S5-C를 건너뛰는 것이 아니다. 균일 격자 경로와 CPU FP64 경로는
둘 다 검증 기준이므로 지우지 않는다.

## S7-0 계측 (2026-09-22)

D10은 "측정 전에는 보장값으로 표현하지 않는다"인데, 프레임 비용은 이 프로젝트에서
한 번도 측정된 적이 없었다. 그래서 먼저 계측을 코드에 넣었다.

- `Simulation/Core/VrgPerfCounters.h` — `DECLARE_CYCLE_STAT`(엔진 프로파일러용)과
  코드로 읽는 누산기를 `VRG_SCOPE_COST` 하나로 같은 스코프에 건다.
  둘이 어긋나면 계측 자체가 틀린 것이다.
- `Simulation/Core/VrgPerfSubsystem.h` — GameInstance 서브시스템. 레벨에 아무것도
  놓지 않아도 PIE와 `-game` 양쪽에서 뜬다. 측정 도구가 레벨 편집 상태에 따라
  있다 없다 하면 단계 간 비교가 안 된다.
- 콘솔: `vrg.Perf.Overlay 0|1`, `vrg.Perf.Capture <초> [라벨] [quit]`.
  후자는 `Saved/Profiling/VrgPerf-<라벨>.csv`와 `.txt`를 쓴다.

**규약 5를 지키는 방식.** 누산기는 게임 스레드 전용이라 잠금이 없다. 그래서
`FAirSolver`와 `FCouplingBridge` 안에서는 전역을 건드리지 않고
`LastPressureSolveMs` / `LastAirSolverMs` 같은 **멤버**에 담아 두고,
게임 스레드 쪽 액터가 그 값을 읽어 프레임 누산기에 더한다.
솔버 안에 둔 것은 스레드 안전한 `SCOPE_CYCLE_COUNTER`뿐이다.
솔버를 워커 스레드로 빼도 계측이 깨지지 않는다.

`RenderCore`와 `RHI`를 Build.cs에 추가했다. `GGameThreadTime`/`GRenderThreadTime`은
RenderCore에 있고, **UE 5.8에는 `GGPUFrameTime` 전역이 없어서**
`GRHIGPUFrameTimeHistory`에서 상태를 들고 하나씩 꺼내야 한다.

### 기준선 (2026-09-22, L_Test, `-game -windowed 1280x720`)

프레임 26개 중 워밍업 6개를 뺀 20개의 중앙값이다.

(옛 성능 표는 2026-10-15 문서 정리 때 삭제했다. 최신 측정은 CLAUDE.md 현재 상태 절.)

프레임당 압력 반복 979회, 디버그 프리미티브 28130개.

**읽는 법.** 프레임의 99%가 Game 스레드이고, 그 안의 95%가 압력 Poisson이다.
`압력 602.86 / 프레임 676.14 = 89%`다. 병목이 압력 솔버라는 것이 이 숫자로 확정됐다.

Draw 44.62 ms도 그 자체로 30fps 선(33.3 ms)을 넘는다. 즉 **솔버를 공짜로 만들어도
지금 표시 방식으로는 22 fps가 상한**이다. 그래서 시각화와 솔버를 둘 다 고쳐야 한다.
GPU 26.12 ms는 렌더링 자체가 가볍다는 뜻이고, 여유가 있으니 연속장을 GPU로 넘길 수 있다.

**이 표가 이후 모든 단계의 비교 기준이다.** 측정값이며 보장값이 아니다 (D10).

## S7-1 온도장 볼륨 렌더링 (2026-09-22)

연속장을 디버그 솔리드 박스 대신 3D 텍스처 + 레이마칭으로 그린다.
**기존 박스 경로는 지우지 않았다.** 같은 온도장을 두 방식으로 그려 비교해야 하고,
박스 경로가 볼륨 경로의 기준이기 때문이다.

- `Source/VrgRender/` — 전역 셰이더 전용 모듈. **별도 모듈로 뺀 이유**는 전역 셰이더 맵이
  엔진 PreInit에서 컴파일되기 때문이다. 게임 모듈(LoadingPhase Default)의 StartupModule에서
  셰이더 디렉터리를 매핑하면 이미 늦어 "Shader source directory not found"로 죽는다.
  이 모듈만 `PostConfigInit`으로 먼저 올려 `/Vrg`를 매핑한다.
- `Shaders/Private/VrgVolumeRaymarch.usf` — 후처리 체인의 Tonemap 지점에 얹는 전체 화면 패스.
  **톤매핑 뒤에 얹는다.** 앞에 얹으면 색상표가 톤매퍼를 거쳐 씻겨 나간다.
- 텍스처에는 **실제 절대온도 K**를 담고(PF_R32_FLOAT) 고체 셀은 음수로 표시한다.
  8비트로 정규화해 담으면 표시 범위를 바꿀 때마다 다시 올려야 하고 범위가 좁을 때 계단이 생긴다.
- 규약 5: 솔버도 액터도 RHI를 건드리지 않는다. 게임 스레드가 만든 복사본을
  `UpdateVolume_GameThread`에 넘기면 렌더 명령이 렌더 스레드에서 올린다.

### 측정 (같은 장면, 900스텝 예열, 1280x720, 옥트리 와이어프레임 끔)

(옛 성능 표는 2026-10-15 문서 정리 때 삭제했다. 최신 측정은 CLAUDE.md 현재 상태 절.)

같은 장을 그릴 때 **Draw 23.22 -> 4.48 ms**다. 드로우 호출은 셀 수와 무관하게 **1개**다.
레이마칭이 GPU에 얹는 비용은 16.72 -> 18.23 ms, 즉 **약 1.5 ms**다.

**박스 모드는 애초에 전부 그리지도 못한다.** `MaxDrawnCells` 때문에 20250셀 중 2014개만
그리고 나머지는 자동 스트라이드로 버린다. 볼륨은 전부 그린다.
**정보는 10분의 1인데 Draw는 5배 비쌌다.**

**기준선 해석을 정정한다.** S7-0의 Draw 44.62 ms는 공기 표시가 아니라
**옥트리 디버그 와이어프레임**이 대부분이었다(프리미티브 28130개 중 거의 전부).
공기 슬라이스 몫은 작았다. 와이어프레임을 끄면 Draw가 4.5 ms로 떨어진다.

### 겪은 것 세 가지 (반복하지 말 것)

1. **픽셀 셰이더 시그니처는 엔진 `ScreenPassVS` 출력과 정확히 같아야 한다.**
   `SV_POSITION`만 받도록 줄였더니 D3D12가 파이프라인 상태를 못 만들었다
   (`E_INVALIDARG`, "Shader compilation failures are Fatal"). 컴파일은 통과하고 PSO에서 죽는다.
   `noperspective float4 UVAndScreenPos : TEXCOORD0`를 먼저 받아야 한다.
2. **`ScreenToTranslatedWorld`에 DeviceZ를 0에 가깝게 넣어 "먼 점"을 만들지 마라.**
   reversed-Z + 무한 원거리 평면에서 그 점이 카메라 근처로 무너져, 광선이 화면 중심을 향한
   방사형이 된다. 진단 모드 4로 확인했다. 뷰 공간에서
   `(ScreenPos.x / ViewToClip[0][0], ScreenPos.y / ViewToClip[1][1], 1)`로 만들면
   투영 규약에 기대지 않는다.
3. **`FSimClock::CompleteStep`만 반복해서 부르면 시계가 멈춘다.** 화면 확인용으로 900스텝을
   앞당기는 `vrg.Air.RunSteps`를 넣었는데, `BeginFrame` 없이 `CompleteStep`만 900번 불러
   누적기가 -18초가 됐고 그 뒤 18초 동안 솔버가 한 스텝도 안 돌았다.
   계측이 "솔버 0.00 ms"를 찍어서 잡았다. 스텝을 앞당길 때도 시계에 같은 시간을 넣어야 한다 (규약 4).

### 검증·재현용 콘솔 명령

레벨 에셋을 고치지 않고 같은 장면을 여러 구성으로 찍을 수 있어야 비교가 성립한다.

```
vrg.Air.DrawSlice 0|1        vrg.Air.DrawVolume 0|1     vrg.Octree.DrawWireframe 0|1
vrg.Air.DrawMode 0|1|2       vrg.Air.MinVisibleFraction <0~1>
vrg.Air.ColorMinC <C>        vrg.Air.ColorMaxC <C>      vrg.Volume.Opacity <1/cm>
vrg.Air.RunSteps <N>         vrg.Air.FrameDomain [거리배수]
vrg.Volume.Debug 0..7        vrg.Perf.Capture <초> [라벨] [quit]
```

`vrg.Volume.Debug`는 1=상자 교차 구간, 2=최대 온도, 3=장면 깊이, 4=광선 방향,
5/6=상자 경계, 7=카메라 위치다. 위 2번 버그를 이걸로 좁혔으므로 남겨 둔다.

## S7-2 기류 시각화 (2026-09-22)

**Niagara를 쓰지 않았다.** 지시는 Niagara GPU 입자였지만, Niagara 입자는 에디터 그래프로
저작한 `UNiagaraSystem` 에셋이 있어야 돌아간다. 그 에셋은 코드로 만들 수 없고 바이너리
`.uasset`이라 리뷰도 안 된다. 같은 결과를 코드만으로 내는 쪽을 택했다.

속도장을 3D 텍스처(PF_A32B32G32R32F, 셀 중심 m/s)로 올리고, **기존 레이마칭 패스 안에서**
속도 반대 방향으로 흘린 좌표에 절차적 값 잡음을 샘플해 줄무늬를 그린다.
줄무늬는 흐름을 따라 움직이고 밝기가 속도 크기다. 입자를 따로 띄우지 않으므로
**드로우 호출은 여전히 1개**다.

MAC 격자라 면 속도를 셀 중심으로 평균해서 넘긴다. 규약 1대로 단위 변환(m/s -> cm/s)은
셰이더 안 한 곳에서만 한다. 속도 정규화 기준은 고정값이 아니라 지금 장의 최대 속도다 —
고정값을 쓰면 느린 구성에서 무늬가 통째로 안 보인다.

**무늬 자체는 연출이며 물리량이 아니다.** 잡음 무늬는 유선(streamline)이 아니고,
`FlowSpeedScale`은 보기 좋으라고 두는 배율이다. 속도의 **방향과 크기**만 화면에 반영된다.

(옛 성능 표는 2026-10-15 문서 정리 때 삭제했다. 최신 측정은 CLAUDE.md 현재 상태 절.)

기류 무늬를 켜도 Draw가 4.48 -> 4.58 ms다. GPU 값의 차이(18.23 -> 14.11)는 실행 간
편차이며 이 표만으로 "기류가 더 싸다"고 읽으면 안 된다.

**정지 화면으로는 움직임을 보일 수 없다.** 무늬는 `View.GameTime`으로 흘러가므로
실행 중에만 확인된다. 스크린샷으로 검증한 것은 "속도가 있는 곳에 무늬가 있고
속도 크기에 비례해 밝다"까지다.

## S7-3 재측정과 4단계 필요 여부 판정 (2026-09-22)

(옛 성능 표는 2026-10-15 문서 정리 때 삭제했다. 최신 측정은 CLAUDE.md 현재 상태 절.)

**표시 비용은 해결됐다.** Draw 44.62 -> 4.58 ms다. 다만 이 중 큰 몫은 옥트리 디버그
와이어프레임을 끈 덕이고, 연속장 표시 자체의 개선은 23.22 -> 4.48 ms다.

**4단계는 필요하다.** 지금 Frame 133.75 ms 중 Game이 129.10 ms로 **96.5%**이고,
그 안에서 압력 Poisson이 101.32 ms로 **프레임의 75.8%**다. Draw는 4.58 ms로
30fps 예산(33.3 ms)의 14%밖에 안 쓴다. 표시를 아무리 더 줄여도 프레임은 7.5 fps에서
움직이지 않는다. D10대로 측정이 판단했다.

(기준선의 676 ms와 지금 134 ms의 차이는 대부분 옥트리 와이어프레임을 끈 것이며,
솔버 자체는 632 -> 130 ms로 줄었다. 이건 최적화가 아니라 **압력 반복 수**가
979회에서 159회로 줄어든 결과다 — 장이 정상 상태에 가까워지면 초기 추정값이 좋아져
Jacobi가 일찍 수렴한다. 같은 조건에서 비교해야 한다는 뜻이기도 하다.)

## S7-4 압력 솔버 컴퓨트 셰이더 (2026-09-22)

균일 격자 압력 Poisson의 **완화 Jacobi 스윕만** 컴퓨트 셰이더로 옮겼다 (FP32).
CPU FP64 경로(`JacobiPoissonSolver`)는 **기준이자 폴백**으로 그대로 있고,
`vrg.Pressure.Gpu`의 **기본값은 0(CPU)**이다. 자동화 테스트는 전부 CPU 경로로 돈다.

- `Shaders/Private/VrgPressureJacobi.usf` — CPU와 **같은 식**을 푼다.
  선형 인덱스 규칙도 `FUniformAirGrid::CellIndex`와 같아야 한다.
  고체 셀과 도메인 밖은 이웃으로 치지 않는다.
- D6: Jacobi다. GPU에서는 읽기/쓰기 버퍼 분리가 선택이 아니라 필수라 오히려 자연스럽다.
  Red-Black이었다면 여기서 통째로 다시 짰어야 한다.

**켜면 공기 솔버가 게임 스레드 전용이 된다.** GPU 경로가 렌더 명령을 밀고 결과를
기다리기 때문이다. 워커 스레드로 빼려면 꺼야 한다. 헤더에 적어 뒀다.

**CPU 경로와 의도적으로 다른 점 두 가지.**
1. CPU는 매 반복 뒤 공기 셀 평균을 뺀다. GPU는 **덩어리마다** 뺀다.
   상수를 더해도 Laplacian이 0이라 잔차가 변하지 않으므로 수렴에 영향이 없다.
   매 반복 리덕션 패스를 두 번 더 도는 것보다 싸다.
2. 반복을 덩어리(기본 `ResidualCheckInterval * 4`)로 나눠 돌리고 덩어리마다 내려받아
   **CPU에서** 평균을 빼고 잔차를 재 D5대로 판정한다. 투영이 CPU에 있어 어차피
   해를 내려받아야 하므로, 잔차 리덕션을 GPU에 또 만들 이유가 없다.
   한 번에 상한까지 돌리면 이미 수렴한 뒤에도 계속 돌고, 매 반복 내려받으면 왕복이 계산을 넘는다.

### 검증 (`vrg.Pressure.Validate`)

같은 입력·같은 초기 추정값(0)에서 두 경로를 따로 풀어 비교한다.
**비트 동일성이 아니라 허용 오차로 본다** (검증 규칙).

```
셀 20250 | CPU FP64 수렴실패 400회 잔차 7.311e-04
         | GPU FP32 수렴실패 400회 잔차 7.311e-04
         | 최대 차이 5.741e-08 / CPU 해 최대 크기 0.112363 기준 정규화 5.110e-07
```

**두 경로의 잔차가 유효숫자 4자리까지 같다.** 해의 차이 5.11e-07은 FP32 머신 엡실론
(1.19e-07) 수준이며, 이보다 더 좁힐 수는 없다.
(둘 다 "수렴실패"인 것은 실시간 설정의 반복 상한 400회에 걸린 것이고, 같은 조건이라
비교 자체는 성립한다. D5대로 실패를 표시하고 있다.)

### 성능 (같은 장면, 20250셀, 1280x720, 볼륨 표시 켬)

(옛 성능 표는 2026-10-15 문서 정리 때 삭제했다. 최신 측정은 CLAUDE.md 현재 상태 절.)

**프레임 이득이 반복 이득보다 큰 이유를 오해하면 안 된다.** 6.4 fps에서는 시계가
매 프레임 `MaxStepsPerFrame`(4)까지 요구해 시뮬이 실시간을 못 따라가고 있었다.
222 fps에서는 네 프레임에 한 번만 스텝이 필요하다. 즉 프레임 35배는
"압력이 35배 빨라졌다"가 아니라 **"실시간을 못 따라가던 상태에서 벗어났다"**는 뜻이다.
공정한 비교는 반복당 10.5배, 스텝당 9.4배다.

**이제 병목이 압력이 아니다.** 스텝당 솔버 11.04 ms 중 압력이 3.23 ms이고
나머지 7.8 ms는 CPU에 남은 이류·부력·투영이다. 더 밀려면 그쪽을 옮겨야 한다.
반복당 0.0607 ms(20250셀)도 GPU 기준으로는 느리다 — 덩어리마다 도는
`BlockUntilGPUIdle`과 내려받기가 대부분이다. 격자를 키우면 이 고정 비용이 묻힌다.

## S7-5 격자 확장과 한계 (2026-09-22)

`vrg.Air.Rescale <배수>`로 **물리 도메인(7.5 x 11.25 x 3.75 m)을 유지한 채** 셀 수만 바꾼다.
셀 폭을 반대로 움직이므로 "같은 방을 더 잘게 푼다"가 된다.
전부 `vrg.Pressure.Gpu 1`, 볼륨 표시 켬, 400스텝 예열 뒤 10초 수집, 1280x720이다.

(옛 성능 표는 2026-10-15 문서 정리 때 삭제했다. 최신 측정은 CLAUDE.md 현재 상태 절.)

### 한계는 셀 수가 아니라 "스텝 비용 20 ms"다

같은 28,050셀 구성이 **60.0 fps와 10.7 fps 두 결과로 갈렸다.** 오타가 아니라 실제 측정이다.
원인은 시계의 되먹임이다.

`FSimClock`은 실제 경과 시간을 누적기에 넣고 고정 스텝으로 쪼갠다. 액터는 한 프레임에
`MaxStepsPerFrame`(4)까지만 소화한다. 즉 한 프레임이 전진시킬 수 있는 시뮬 시간은
**4 x 0.02 s = 0.08 s**다. 프레임이 80 ms를 넘으면 빚이 매 프레임 늘고, 한 번 밀리면
영원히 4스텝/프레임에 고정된다. 반대로 한 번 따라잡으면 네 프레임에 한 번만 스텝이 필요해
프레임이 확 가벼워진다. **두 상태가 다 안정적이라 같은 설정이 양쪽으로 갈린다.**

경계 조건은 셀 수가 아니라 **스텝 하나가 20 ms(= 0.08 s / 4) 안에 끝나는가**다.
28,050셀이 딱 그 근처라 갈린다.

**따라서 "30fps를 지키는 최대 셀 수"는 약 28,000셀이되, 그 근처는 불안정하다.**
여유를 두려면 23,000셀(63.4 fps, 셀 폭 0.24 m)이 안전한 상한이다.
33,390셀은 27.5 fps로 최저선을 못 지킨다.
**측정값이며 보장값이 아니다** (D10). 장면·카메라·예열 상태가 바뀌면 달라진다.

### 읽을 때 주의할 것

- **`ms/Jacobi 반복`이 구성마다 2~3배씩 튄다.** 4스텝/프레임에 고정된 구성에서 더 크다.
  GPU는 덩어리(32회)마다 `BlockUntilGPUIdle`로 동기화하므로, 반복 수가 적은 스텝일수록
  고정 비용이 반복당 단가에 크게 실린다. 셀당 처리량이 아니라 **덩어리 왕복 비용**이 보이는 것이다.
- 8만 셀 위에서는 반복당 비용이 셀 수에 거의 선형이다 (0.147 -> 0.230).
  그 아래는 고정 비용에 묻힌다.
- **볼륨 텍스처 업로드는 시뮬 스텝마다만 한다.** 처음에는 매 프레임 올렸는데,
  프레임이 스텝보다 잦으면 같은 값을 여러 번 올린다. 다만 큰 격자에서는 어차피
  매 프레임 스텝이 돌아 이 중복 제거가 효과가 없다. 큰 격자의 Draw 60 ms는
  스텝마다의 업로드 자체이며, 줄이려면 부분 갱신이나 포맷 축소가 필요하다 (아직 안 했다).
- 기류 무늬를 끄면 속도 텍스처(복셀당 16바이트, 온도의 4배)를 아예 만들지도 올리지도 않는다.

### 남은 병목

162,000셀에서 Game 441 ms / Draw 62 ms / GPU 75 ms다. 압력은 GPU로 갔지만
**이류·부력·투영이 아직 CPU FP64**이고 그게 Game의 대부분이다.
다음에 밀 곳은 거기이며, 그때는 속도장도 GPU에 상주시켜 스텝마다의 왕복을 없애야 한다.

### 표시 파라미터를 역산해서 정했다

"볼륨이 안 보인다"와 "화면이 통째로 파란 벽이다"가 둘 다 표시 파라미터 문제였다.

- **자동 색상 범위**(`bAutoColorRange`, 기본 켬) — 장의 실제 최소/최대 온도에 맞춘다.
  고정 범위(24~45 °C)에 공기가 24~34 °C면 정규화가 0.5를 못 넘어 거의 투명해진다.
- **`AutoColorSpanFraction` 0.6** — 상한을 (최소 + 0.6 x 폭)으로 좁힌다.
  가장 뜨거운 셀에 상한을 맞추면 그 한 셀만 빨강이고 방 전체가 파랗게 보인다.
- **`VolumeFloorDensity` 0.07 / `VolumeOpacityPerCm` 0.0035** — 도메인 대각선이 약 1400 cm라
  `밀도 x 흡수 x 경로`가 알파의 지수가 된다. 0.35 x 0.02 x 1400 = 9.8이면 완전히 막혀
  파란 벽이 된다. 찬 공기 알파 약 0.3, 뜨거운 공기 약 0.99가 되도록 역산했다.
- **`FlowStrength` 0.025** — 0.08에서는 기류 무늬가 온도 색을 덮어 화면이 하늘색이 됐다.
  주인공은 온도이고 무늬는 "여기 공기가 움직인다"만 알려주면 된다.
- **색상표 기본을 CFD 무지개**(파랑->청록->초록->노랑->빨강)로 바꿨다.
  열화상(검정->보라)은 찬 공기가 검게 투명해져 방 전체 분포가 안 읽힌다.
  `VolumeColorMap` 1로 되돌릴 수 있다.

**이 값들은 전부 표시용이며 계산에 쓰이지 않는다.**

### 계측이 에디터 PIE에서 거짓말을 하고 있었다

오버레이가 `Game 23125.47 ms | Draw 0.00`을 찍었다. 프레임이 629 ms인데 게임 스레드가
23초일 수 없다. 엔진 전역 `GGameThreadTime`/`GRenderThreadTime`이 에디터 PIE에서
갱신되지 않아 나온 값이다.

게임 스레드 시간은 이제 **직접 잰다** — `OnBeginFrame`~`OnEndFrame` 구간을 잰다.
렌더 스레드 값은 엔진 전역을 읽되 말이 안 되면(0이거나 프레임의 5배 초과) `-`로 적는다.
솔버 비중도 게임 스레드 대비가 아니라 **프레임 대비**로 적는다
("게임의 3%" 같은 오해를 부르는 수치가 나왔다).

## 2026-10-27 공기 유선·평면·화살표 보기 (교수님 streamtrace 그림)

교수님이 보여 준 그림(칸막이 수조의 스트림튜브를 속도로 색칠한 3D 보기 + 평면 보기)을 게임 화면에 만들었다. 데모(순간 흐름, 디버그 선)를 사용자에게 보인 뒤 본 구현.
- 계산: `Simulation/Air/AirStreamlines` - 면 속도를 보간한 속도장의 방향(dx/ds = u/|u|)을 RK4로 5 cm씩 적분, 고체·방 밖·0.02 m/s 미만·40 m에서 멈춤, 점마다 속력·온도.
  평면용은 수평 성분만(`bPlanar`). `Simulation/Air/AirFlowAverager` - 최근 30 s를 1 s 블록(속도·온도 × 스텝 dt의 합)으로 모아 평균(규약 4, 스텝 크기와 무관하게 정확).
  평균은 유선·평면·화살표 모드가 켜져 있을 때만 모은다(스텝마다 면 배열 한 번). 표시 전용: 솔버는 건드리지 않는다.
- 시작점: CRAH 토출면마다 3 × 5, 랙 뒤(배기) 0.5·1.1·1.7 m. 랙 몸체가 공기 격자에서 고체(팬은 덕트)라 CRAH에서 출발한 선은 랙 앞에서 끝나므로 뜨거운 쪽은 따로 출발시킨다.
- 표시(`V`로 순환, `vrg.Air.View 0~5`): 온도 볼륨 → 유선·속도(0~2 m/s) → 유선·온도(18~40 °C) → 유선(속도)+볼륨 → 평면 보기 → 화살표(0.375·1.125·1.875 m, 두 칸마다).
  튜브는 지름 3 cm 원기둥 10 cm 조각을 32색 띠로 묶은 인스턴스(`AAirFlowDisplayActor`, `PlantInstances`), 범례는 HUD 오른쪽 아래(모드·평균 시간·색 막대·값 5개).
  평면 보기: `vrg.Air.PlanHeight`(기본 1.1 m) 층의 온도 색 칸과 그 층의 수평 유선(흰색), 카메라를 방 위로 옮기고 다음 모드에서 되돌린다. 1 s마다 다시 계산.
- AI 화면 확인(2026-10-27): 유선·속도(그림처럼 CRAH에서 나와 랙으로 도는 고리, 범례 "시간 평균 30 s"), 유선·온도, 유선+볼륨, 화살표, 평면 보기, 배치 모드에서 모두 사라짐.
  프레임(15 s, 측정값) 유선·속도 중앙 16.9 ms / 95 % 19.6 ms, 온도 볼륨 18.7 / 21.6 ms(유선 모드가 볼륨 레이마칭보다 가볍다).
  찾은 것 1: 평면 단면이 제 높이(1.1 m)에서는 콜드아일 지붕·랙 윗면·배관에 가려 위에서 안 보였다 → 그림만 방 꼭대기 + 2 m에 띄워 그린다(데이터는 1.1 m 층 그대로).
  찾은 것 2: 볼륨을 끈 모드에서 위에서 내려다보면 화면이 통째로 검었다. 바탕화면 캡처에는 직전 화면이 남아 헷갈렸고 엔진 스크린샷(`HighResShot`)으로 검은 화면을 확인했다.
  원인은 볼륨 후처리 패스(`FVrgVolumeSceneViewExtension`)가 꺼져 있을 때 입력을 그대로 돌려주기만 한 것 - 이 패스가 체인의 마지막이면 엔진이 준 출력(OverrideOutput, 백 버퍼)에 써야 하는데 아무것도 안 써서 검게 나왔다(시점에 따라 마지막이 됨). 꺼져 있을 때도 장면을 그 출력에 복사하게 고쳤다. `vrg.Air.DrawVolume 0`으로도 나던 기존 결함이다.
  찾은 것 3: 범례 설명 줄이 상자를 넘쳐 글자 폭에 맞췄다.
- 범위 0~2 m/s·18~40 °C는 표시 선택값이다(모델 한계 아님). 유선은 한 시점(30 s 평균장)의 그림이고 입자가 실제로 간 길(경로선)은 아니다. 공기는 Boussinesq라 밀도는 온도로 정해져 따로 칠하지 않았다.
